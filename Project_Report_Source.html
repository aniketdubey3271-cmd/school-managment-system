Project overview

Abstract

Schools often maintain student details, attendance, grades, assignments and notices in separate registers or disconnected files. This makes routine administration slow, increases repeated data entry and makes it difficult for students and teachers to find current information. The Student Management System addresses this problem through a single browser-based application with separate administrator, teacher and student portals. Administrators manage users, classes, subjects, announcements and reports. Teachers work with assigned classes to record attendance and grades, create assignments and review student submissions. Students can view their own academic information, announcements and assignments and submit work online. The application is implemented in Java 21 using Spring Boot, Spring MVC, Spring Security, Thymeleaf, Spring Data JPA, Hibernate, Flyway and SQLite. BCrypt is used for password hashing, and role-based authorization restricts access to portal routes. The project demonstrates how a layered web application can connect a responsive user interface to services and a relational database. It is intended as an academic prototype and a foundation for future improvements such as persistent cloud storage, email verification, PostgreSQL deployment and a native Android client.

Keywords: school management, role-based access control, Spring Boot, SQLite, attendance, assignments, academic reports

Chapter 1

Introduction

1.1 Background

Educational institutions manage interconnected information about learners, staff, classes, subjects and academic activity. When these records are stored in separate paper registers or spreadsheets, staff may need to copy the same data several times. Students may also depend on a teacher or office visit to confirm attendance, marks, assignment deadlines or school announcements. A shared information system can make these routine records easier to maintain and access.

Web applications provide a practical way to offer a common system through standard browsers on desktop computers, tablets and phones. A responsive web portal can therefore support mobile access without being a native Android app. The system developed in this repository uses this approach: one Spring Boot application serves role-specific pages to administrators, teachers and students.

1.2 Project purpose

The purpose of the Student Management System is to bring common school administration and classroom workflows into one application. It combines user accounts, role-based dashboards, class and subject configuration, attendance, grading, assignments, submissions, announcements and reports. Data is organized in a relational SQLite database and accessed through Spring Data JPA repositories.

1.3 Scope

  • Administrators maintain teachers, students, classes, subjects and announcements, and view school and class reports.
  • Teachers access assigned classes, record attendance and marks, publish assignments and announcements, and review submissions.
  • Students access their own profile, attendance, grades, announcements and assignments, and submit assignment files.
  • The application supports account sign-in, role-based redirection, password hashing, input validation, file-size/type restrictions and generated PDF report cards/ID cards.

1.4 Project boundary

The application is a web-based academic prototype. It does not include a native Android client, email verification, password reset by email, payment processing, school-wide multi-tenancy or an external identity provider. The current configuration uses SQLite and local file storage, so production deployment requires durable database and upload storage planning.

Chapter 3

System Analysis

3.1 Existing system

In a manual or fragmented workflow, a school might use separate registers for attendance, spreadsheets for grades, messaging groups for notices and individual folders for assignments. This can create duplicated records, delayed updates, inconsistent formats and difficulty producing consolidated reports. Access to a record may depend on the availability of the person or document that stores it. These observations describe the common problem domain; they are not a formal audit of a specific institution’s current process.

3.2 Proposed system

The proposed system provides one authenticated browser portal backed by shared application services and a relational database. Each role sees functions suited to its work. Administrators configure school data and oversee reports; teachers manage academic activity for their assigned classes; students view their own information and submit work. The system uses server-side authorization and service-level ownership checks to protect requests and data.

3.3 Feasibility study

Technical feasibility

The project uses mature, open-source Java technologies and a standard browser interface. Java 21 and Maven provide the runtime/build foundation; Spring Boot combines the application components; SQLite minimizes setup for a small prototype. Docker packages the application for cloud hosting. The design is technically feasible for an academic demonstration. A larger school deployment would need stronger operational storage, backups, monitoring and likely a managed database.

Operational feasibility

Users interact with familiar web forms and dashboards. Role separation reduces unrelated options on each portal. Administrators must configure classes, subjects and user accounts before teachers and students can use all workflows. Basic training and clear onboarding would support adoption.

Economic feasibility

The code uses open-source frameworks and can be demonstrated locally without paid software licences. Hosting may be available on a free tier, subject to that provider’s current limits. Free container services can sleep when idle and may not provide durable local filesystems; they are suitable for demonstration but should not be assumed to provide production-grade availability or data retention.

Schedule and risk considerations

The project is organized into authentication, administration, teacher, student, reporting and shared-infrastructure modules. Key risks include lost local data on ephemeral hosting, unverified public account details, file-storage durability, and the mismatch between an Android-specific report format and the actual web implementation. These are documented as limitations and future work.

The application follows a layered MVC design. Thymeleaf renders HTML pages from controller-provided models. Controllers handle HTTP requests and form binding; services enforce workflow rules; Spring Data repositories perform persistence; JPA entities map records to tables. Spring Security authenticates users and applies route rules. Flyway applies schema migrations when the application starts.

4.9 Data integrity rules

  • Usernames and email addresses are unique.
  • A student roll number is unique within the same class.
  • Attendance is unique per student and date.
  • A grade is unique per student, subject and exam type.
  • A student may have one submission per assignment; resubmission updates the existing record.
  • A class/subject pair may have one teaching assignment in the schema.
  • Foreign keys connect profiles and academic records to their parent records; Flyway migrations define the schema.

6.4 Role-specific functionality

Administrator

Creates and updates student and teacher accounts, configures class/section and subject records, links teachers to class-subject assignments, publishes school/class announcements and reviews reports. The initial administrator is created only when none exists and an admin password is configured.

Teacher

Works with assigned classes and subjects, records attendance and grades, creates assignments with deadlines, reviews student submissions, publishes permitted announcements and views teacher-scoped reports. Service logic limits actions to the teacher’s assigned classes and subjects.

Student

Views own profile, attendance, marks, assignment details and announcements. A student can upload and resubmit assignment work subject to class membership, deadline and file validation. Students cannot access teacher or administrator portal routes.

Public registration

The sign-up form offers Student, Teacher and Administrator choices and dynamically displays role-specific fields. Student registration collects class and roll number; teacher registration collects specialization/contact; administrator registration uses an invitation code. Separate server-side invitation codes are configured as SMS_TEACHER_SIGNUP_CODE and SMS_ADMIN_SIGNUP_CODE. These codes prevent unauthenticated visitors from freely granting themselves staff or administrator privileges. The current student form does not verify the submitted identity against an external school roster.

6.5 Security and validation

  • Form-based sign-in accepts username or email; user passwords are stored as BCrypt hashes.
  • Role rules restrict /admin/**, /teacher/** and /student/** routes.
  • Service checks enforce ownership and class/subject boundaries for teacher and student actions.
  • Bean Validation and business checks protect form input; uniqueness rules are enforced in service/database logic.
  • Uploaded files are restricted by extension and size and stored under generated names.
  • CSRF protection is provided by Spring Security’s default form configuration.

6.6 Deployment configuration

The Dockerfile uses a Maven build stage and a Java 21 runtime stage. Maven is configured to use a Google-hosted mirror of Maven Central for artifact resolution, with bounded retries for HTTP 429 rate limits. The runtime listens on the hosting platform’s PORT. Render can build the Dockerfile from the repository. The current SQLite file and upload directory are local paths; they need persistent volumes or replacement managed services before production use.

Chapter 9

Conclusion and Future Enhancements

9.1 Conclusion

The Student Management System demonstrates how a layered web application can organize common school workflows under a shared sign-in and data model. Its administrator, teacher and student portals provide different capabilities while reusing business services and database records. The project brings together Java programming, MVC web development, persistence, schema migration, authentication, access control, validation, file handling, PDF generation and container packaging.

The work also illustrates the importance of accurately matching a project deliverable to its academic format. The supplied template is for Android development, whereas this repository contains a responsive web application. The project should be presented as a web system unless a separate Android client is implemented and approved by the guide.

9.2 Learning outcomes

  • Organizing an application into controller, service, repository and entity layers.
  • Designing relational entities, keys, constraints and incremental schema migrations.
  • Implementing authentication, BCrypt password hashing and role-aware route security.
  • Building and validating data-entry workflows with Spring MVC and Thymeleaf.
  • Applying authorization rules to class ownership and student-specific records.
  • Generating documents and handling validated assignment uploads.
  • Containerizing an application and identifying the operational risks of ephemeral storage.
  • Documenting functionality and tests without claiming unverified results.

9.3 Future enhancements

  1. Persistent production storage: migrate SQLite to PostgreSQL and assignment files to durable object storage; add automated backups and recovery procedures.
  2. Native Android client: design a mobile API, token-based authentication and Android screens if a native mobile deliverable is required.
  3. Account verification: verify student identity against an administrator-maintained roster; add email verification, password reset and account approval.
  4. Improved staff onboarding: issue time-limited invitations or require administrator approval for teacher and administrator accounts.
  5. Operational security: configure HTTPS, rate limiting, audit logs, secret rotation, security headers and monitoring.
  6. Accessibility and UX: complete keyboard/screen-reader checks, improve mobile data-entry flows and localize date/number formats.
  7. Additional school functions: timetable, fees, parent/guardian portal, messaging, academic calendar and exportable spreadsheets.
  8. Quality assurance: automate the complete test suite in CI, add browser-level acceptance tests and conduct usability evaluation.
